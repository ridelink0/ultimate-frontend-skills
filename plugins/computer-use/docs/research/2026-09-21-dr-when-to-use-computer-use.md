# Why Claude didn't reach for Computer Use, and the fix

## Deliverables (read this first)

**Rewritten SKILL.md frontmatter description** (950 of 1024 allowed characters [^3]):

```yaml
---
name: computer-use
description: Use any time something on this computer needs looking at or operating instead of being left for the user to do by hand: reading what a window, dialog or menu says; reading a settings/preferences panel inside an app to confirm a value such as a config file path (e.g. Windsurf's Cascade > MCP > Configure screen); checking whether an app is open or what state it's in; clicking, typing, filling a form, testing a GUI, confirming a change rendered; opening or closing a window, including a stray window on a second virtual desktop (closing works there today without switching the user's screen); or driving any app with no CLI or API. Also whenever the user names an application, a window or a settings screen, or says "look at my screen", "open X", "close X", "click X". Before listing anything as "for you to do", check it against this skill first. Windows and macOS; reads windows without disturbing them, and can work while the user keeps working.
---
```

Changes from the current description: adds a named worked example (the exact Windsurf/Cascade/MCP case that failed today), names the cross-desktop-close capability explicitly instead of leaving it implicit, adds an imperative "check it against this skill first" clause, and adds the bare verbs a user actually types ("open X", "close X", "click X") — this is the skill-creator's own documented fix for "undertriggering" [^5].

**Trigger situations for a hook** (a prompt-time list, and a response-time list — see Finding 3 for why both are needed):

UserPromptSubmit trigger (regex over the incoming `prompt` field, no LLM call):
1. Names a known GUI application, IDE, or browser (Windsurf, VS Code, Chrome, Spotify, Notepad, etc. — maintain as a list, or fall back to Title Case proper-noun heuristics)
2. Contains "settings", "preferences", "options", "config panel", "Configure", "MCP", or similar app-configuration nouns
3. Contains "dialog", "popup", "menu", "dropdown"
4. Contains "window" as a noun (not "Windows" the OS) combined with a verb: open/close/move/find/switch to
5. Verbs "open", "close", "click", "type into", "check if X is running/open"
6. "look at my screen", "what does it say", "confirm it shows"
7. Any task phrased as a manual GUI walkthrough with no CLI equivalent named (heuristic: mentions clicking through a UI and no `npm`/`git`/API/CLI token anywhere in the same prompt)

Stop-hook trigger (regex over Claude's own final response text — this is the one that actually catches today's failure, see Finding 3):
1. Response contains "for you to do", "left for you", "you'll need to", "you should", "please open/close/click/check", "manually" + a GUI noun (window, panel, settings, dialog, app, desktop, screen) in the same list item or sentence.

**Three-line "before you hand anything back" rule** (goes in the skill body, Level 2, so it costs nothing unless the skill already triggered):

> Before any step is written under "for you to do" / "left for you" / "you'll need to", ask: can `computer-use` do this directly — read it, click it, open it, close it?
> If yes, do it now and report what happened; a completed action is not a follow-up.
> Only list a step for the user if it needs their credentials/consent (blocked or hand-off tier) or has no GUI/CLI path at all.

**Ranked changes, one line each, highest impact-per-token first:**

1. Add a **Stop hook** that regex-scans Claude's own outgoing response for the handback pattern above and blocks the turn once with a corrective nudge — this is the only mechanism that fires exactly when the failure happens, costs ~0 tokens on the (overwhelming) majority of turns that don't match, and doesn't depend on the skill having been loaded at all [^6][interpretation].
2. Rewrite the **SKILL.md description** with the named Windsurf/settings-panel example, the cross-desktop-close capability, and bare-verb triggers — paid once per session as ~100-150 extra metadata tokens (Level 1 is always loaded [^1]), raises the odds Claude reaches for the tool mid-task rather than only at the end [^2][^5].
3. Add the **three-line rule** to the skill body — zero cost when the skill isn't triggered, but only helps once #2 or #1 has already gotten the skill or the tool into play; it's a backstop, not a trigger.
4. Add the **UserPromptSubmit keyword hook** — genuinely cheap (a hook runs outside the context window entirely [^19]) but structurally weaker for *this* failure mode, because the failure happens at the end of an already-running task, not at the prompt that started it; still worth having for the broader "reach for the tool" goal Gev's memory already states [^41].
5. Do **not** add more prose to memory/CLAUDE.md for this — a rule already exists there [^41][^42] and evidently wasn't enough on its own; Anthropic's own guidance is explicit that CLAUDE.md-style prose "carries the highest token cost" for the least reliability compared to a hook, precisely because a hook enforces deterministically and prose has to be noticed and applied by the model every time [^19][interpretation].

## Key points

### 1. Skill selection is 100% a model judgment call, with no tie-breaking mechanism · Confidence: high
Claude Code loads only `name` + `description` for every installed skill at session start (~100 tokens each), and Claude itself — reading that metadata as plain text in its own system prompt — decides whether a request matches well enough to invoke a skill; there is no separate ranking engine, and overlapping/vague descriptions are a documented authoring failure, not something the harness resolves [^1][^2][^3]. There is a real precedence system, but it only resolves *same-name* collisions across enterprise/personal/project/plugin scopes — it says nothing about two differently-named skills both plausibly matching one request [^3].

### 2. Anthropic's own skill-authoring guidance names this exact failure and prescribes over-correcting for it · Confidence: high
The official skill-creator meta-skill states Claude has "a tendency to 'undertrigger' skills — to not use them when they'd be useful," and instructs authors to make descriptions "a little bit 'pushy'," worked example included [^5]. The best-practices doc separately requires an explicit "Use when..." clause naming concrete triggers/file types, third-person phrasing (first/second person "can cause discovery problems" because the description sits in the system prompt), and flags vague descriptions like "Helps with documents" as a named bad pattern [^2]. The existing Better Computer Use description is reasonably specific but never names the concrete failure case (a settings *panel* specifically, or cross-desktop close) — it relies on the general "driving any app with no CLI" clause to cover them by inference, which the undertriggering finding says is exactly the gap that needs closing with an explicit example [^5][interpretation].

### 3. UserPromptSubmit cannot use a matcher and fires on every prompt — but a Stop hook can gate completion itself · Confidence: high
`UserPromptSubmit` "fires on every prompt submission (if you add a matcher, it's silently ignored)" — selective firing has to be implemented inside the script itself, and the documented best practice is "Exit 0 silently if you have no context to add" [^17]. Separately, Claude Code's own best-practices doc documents a stronger mechanism for exactly this situation: a Stop hook is "a deterministic script gate that blocks the turn from ending until it passes," with the harness overriding it only after 8 consecutive blocks — described as "what let an unattended run finish correctly without you" [^6]. This means the more surgical fix for a *handback-list* failure (which happens at the end of a task, not the start) is a Stop hook that inspects the response Claude is about to send, not a UserPromptSubmit hook that only ever sees the original request [^6][^17][interpretation].

### 4. Hooks are documented as the cheap mechanism precisely because they bypass the context window; prose (CLAUDE.md/memory) is the expensive one · Confidence: medium
Anthropic's own "Steering Claude Code" post states hooks "operate outside the context window entirely, making them the most economical choice for deterministic automation," contrasted with CLAUDE.md, which "carries the highest token cost" because "every line loads into every session ... whether it's relevant to their task or not" [^19]. No Anthropic-published exact token-cost number for a hook injection was found; third-party estimates (200-800 tokens per always-firing hook, ~2,400 tokens for four of them, ~20-30k tokens of fixed per-session overhead before the user even types) exist but could not be independently re-fetched this session and are UNVERIFIED [^20][^21]. The qualitative conclusion — a conditional, mostly-silent hook costs close to nothing, and an always-on prose rule costs a little on every single turn regardless of relevance — is primary-sourced even though the exact numbers aren't [^19].

### 5. OpenAI's Astra guidance is a safety denylist and runtime manual, not a "when to reach for the tool" triage list · Confidence: high
Direct, full reads of all four Astra/Codex computer-use documents on this machine — `api.md` (pure method reference), `confirmations.md` (a 4-tier confirm/hand-off policy for *how* to act, not *whether* to), `guidance.md` (node_repl/@oai/sky mechanics + a "Non-negotiable Windows Automation Safety" denylist), and `unified-computer-use`'s `.mcp.json`/`plugin.json` — found **no** enumerated "reach for GUI automation when you see a settings panel / a named window / a dialog / anything with no CLI" list anywhere [^30][^31][^32][^34]. The one explicit cross-tool preference statement found in the entire bundle is narrower and different in kind: an env var telling the model to "Prefer this method of controlling Chrome over alternatives (such as Computer Use) unless the user explicitly mentions an alternative" — a browser-specific routing rule, not a general trigger list [^34]. `guidance.md`'s only "when" content is negative (never automate a terminal, the Run dialog, password managers, security apps, or the ChatGPT/Codex UI itself) [^32]. This matches an existing local research document (dated today, in the same repo) that independently reached the same conclusion while doing a full Astra-vs-Gev's-plugin parity pass [^38].

### 6. Both concrete failure cases from today are things the plugin can already do — the report should have said so, not deferred them · Confidence: high
Reading a settings dialog: `computer_snapshot` reads any window's accessibility tree "free" (no grant needed), a settings dialog opens its own window/hwnd readable the same way as any other window, and an editor like Windsurf is classified tier `shell` — "readable, never typeable" — which covers reading a settings screen (no typing required) [^35][^36]. The one documented failure mode is "BLIND TREE" on an Electron app whose renderer accessibility bridge is off, fixable with `--force-renderer-accessibility`, with a screenshot fallback (`computer_screenshot` / `with_image: true`) when the tree truly can't be read [^35][^36]. No app-specific carve-out exists for Windsurf/Cascade/MCP by name in either doc — this is generic tooling, so the specific dialog is UNVERIFIED without an actual test run, but nothing documented would have blocked reading it [^37, sq5 scraper finding]. Closing a stray window on a second virtual desktop: verified directly against the source (`server/index.mjs:581-586, 1581-1596`) that `computer_close_window` only refuses a cross-desktop close when the install's `DESKTOP_SCOPE` setting is `'current'`; the shipped default is `'all'`, under which the close call proceeds straight to `driver.call('close_window', {hwnd, mode})` [^37]. This is consistent with the README's own documented limit — Windows serves the *frame* (title bar, minimise, maximise, **close**) of a window on a desktop you aren't looking at, just not its contents — so closing doesn't require switching the user's screen at all [^35]. Windows itself backs this: `IVirtualDesktopManager` exists specifically because a window on another desktop remains a fully addressable object to any process holding its handle, and neither `DestroyWindow` nor `WM_CLOSE`/`PostMessage` documents any virtual-desktop-scoped restriction [^22][^23][^26][^27].

### 7. Other frameworks encode "verify/act before handing back" as an explicit second pass, not a single model's self-restraint · Confidence: medium
Cursor's docs ship a dedicated verifier-subagent pattern specifically to catch "AI marks tasks as done but implementations are incomplete," instructed to "not accept claims at face value, test everything" [^13]. Devin 2.2 runs its own change with "computer use" and sends back screen recordings before treating a PR as reportable [^14]. Microsoft's Magentic-One paper documents the mirror-image failure directly: agents "did not utilize available data, tools, or resources effectively... even when automation was an option," including "manual downloads persisting when FileSurfer was available" — the same failure class as today's Windsurf/window handback [^16]. The common structural answer across these is a distinct check *after* the main agent thinks it's done, not a single pass that's supposed to remember everything — which supports ranking the Stop-hook gate above the in-skill prose rule (Finding 3, deliverable #1 vs #3) [^13][^14][^16][interpretation].

## Executive Summary

Claude didn't reach for Computer Use today because nothing forced a check at the moment it mattered: skill selection is a pure model judgment call with no fallback ranking [^1][^3], the existing description never named "a settings panel" or "a window on another desktop" as concrete triggers even though it covers them in principle [^2][^5], and Claude Code's only prompt-time hook (`UserPromptSubmit`) fires on the user's *opening* prompt, not on Claude's own closing response — so it structurally cannot catch a handback list written at the end of a task [^17]. Both items Claude left behind are things the plugin already does: reading a settings dialog is ordinary tree-reading on a `shell`-tier app [^35][^36], and closing a window on a second virtual desktop is not blocked by the plugin's own code under the shipped default scope, verified directly in `server/index.mjs` [^37]. OpenAI's own Astra bundle offers no enumerated "when to use GUI automation" list to imitate — its guidance is a safety denylist plus API mechanics, and a same-day local research document already reached this same conclusion independently [^30][^32][^38]. The single highest-leverage, lowest-token fix is a Stop hook that scans Claude's own outgoing response for the handback pattern and blocks completion once to force a self-correction — the exact "verify before reporting done" pattern other agent frameworks (Cursor, Devin, Magentic-One's negative case) already encode structurally rather than trusting model discipline alone [^6][^13][^14][^16].

## Findings

### How Claude Code decides to invoke a skill

Metadata-only loading, model-driven matching, no keyword engine: at startup only `name` and `description` are pre-loaded (Level 1, ~100 tokens/skill); the full SKILL.md body loads only once Claude decides the skill is relevant (Level 2) [^1]. The `description` field is explicitly "what Claude matches your request against" [^1] and is "critical for skill selection: Claude uses it to choose the right Skill from potentially 100+ available Skills" [^2] — there is no fixed keyword/regex matching layer documented anywhere in the primary sources checked [^1][^2][^3][interpretation]. Required frontmatter validation: `description` must be non-empty, max 1024 characters, no XML tags, and "must include both what the Skill does and when Claude should use it" [^2]. The combined `description` + `when_to_use` text is separately truncated at 1,536 characters in the actual skill listing shown to Claude, an even tighter practical ceiling on how much disambiguating detail Claude ever sees [^3]. Users can always force-invoke any skill directly with `/skill-name` regardless of whether the description would have matched, and a skill author can opt out of automatic invocation entirely with `disable-model-invocation: true` [^3].

Competing skills are resolved by the author, not the runtime: the *only* documented deterministic precedence system covers same-*name* collisions (enterprise > personal > project; a plugin skill is auto-namespaced `plugin:skill-name` so it can never collide by name with anything else) [^3][^4]. For two differently-named, differently-owned skills whose descriptions both plausibly match one request, no tie-breaking rule exists in any primary source checked — the documented remedy is for the *author* to narrow the description until it stops overlapping, verified by watching real behavior and asking "does the Skill activate when expected?" [^2][interpretation]. Anthropic's skill-creator meta-skill goes further and explicitly instructs authors to test "uncommon use cases where the skill competes with others but should win" as part of writing the description in the first place [^5].

Writing a description that fires reliably: skill-creator names the concrete failure mode ("undertriggering") and prescribes "pushy," assertive language, giving a canonical before/after rewrite: turning a plain capability sentence into one that says "Make sure to use this skill whenever the user mentions X, Y, or Z, even if they don't explicitly ask for it" [^5]. Best-practices adds: write in third person (first/second person "can cause discovery problems" because the text is injected verbatim into every session's system prompt) [^2]; be specific with named triggers rather than generic capability statements — its own worked examples all follow an "X. Use when the user asks for Y, mentions Z, or works with W files" template [^2]; and avoid vague descriptions like "Helps with documents" or "Processes data," which are named as failure examples in the docs themselves [^2].

### What Astra's own guidance says (and doesn't say)

All four on-disk Astra/Codex documents were read in full this session: `api.md` (141 lines, pure `sky` method signatures, zero "when to use" language) [^30]; `confirmations.md` (89 lines, a 4-tier Hand-Off/Always-Confirm/Pre-Approval/No-Confirmation policy governing risk once already acting, not a trigger list for acting at all) [^31]; `guidance.md` (261 lines: node_repl/@oai/sky runtime mechanics, an observe-act-refresh loop, screenshot-handling rules, and a hard safety denylist) [^32]; and `unified-computer-use`'s plugin config, which turns out to be a *separate*, browser-only automation surface ("App-managed browser automation runtime"), not a general-desktop GUI plugin at all [^34]. None of the four contains anything resembling "use this when you see a settings panel / a window the user names / a dialog / anything with no CLI" [^30][^31][^32][^34][interpretation]. The single explicit cross-tool steering statement anywhere in the bundle routes Chrome control specifically toward the browser plugin over "Computer Use," and only "unless the user explicitly mentions an alternative" [^34] — the opposite direction of what this research went looking for (a rule that pulls the model *toward* GUI automation), and scoped to one browser, not general desktop apps.

A same-day, same-machine research document (`docs/research/2026-09-21-dr-computer-use-vs-astra.md`, a prior deep-research pass in this same repo comparing the two plugins tool-by-tool) independently reached the identical conclusion and goes further: it documents that Astra's Windows implementation "runs on the active desktop... can't operate in the background," has **no** documented virtual-desktop targeting capability at all (the only workaround OpenAI publishes is running the entire ChatGPT app inside a separate Windows VM), and has **no close-window method whatsoever** among its 13 bundled tool methods [^38]. Its companion TODO file states this even more plainly for the cross-desktop scenario specifically: "Astra never targets [a second desktop] and documents no cross-desktop action; its only workaround is a whole VM" [^39]. This means Astra is not a source of positive guidance to imitate for either of today's two failure cases — it structurally cannot do either one, so its docs never needed to tell the model when to try [^38][^39][interpretation].

### Hook design: what fires when, and at what cost

`UserPromptSubmit` receives `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, and the `prompt` text itself; its stdout (plain text) is "added as context that Claude can see and act on," uniquely among hook events where stdout normally only goes to a debug log [^17]. It explicitly has "no matcher support... fires on every prompt submission" — any selective behavior has to be coded inside the hook script by inspecting the `prompt` field itself [^17], which is exactly the pattern the plugin's existing `appshot.mjs` already uses: it reads a flag file and stays completely silent unless a fresh, unconsumed appshot exists, costing nothing on the vast majority of turns [^40]. The documented best practice reinforces this: "Exit 0 silently if you have no context to add (no output needed)" [^17], and the default timeout is a tight 30 seconds specifically because this hook runs synchronously before *every* prompt [^17].

For the *other* half of the problem — catching a bad response before it goes out, not a request coming in — Claude Code documents a stronger primitive: a **Stop hook** can "block the turn from ending until it passes," and is explicitly named (alongside `/goal`) as "what let an unattended run finish correctly without you" [^6]. The plugin already has a working Stop hook wired to `computer_turn_ended` [^40] — proving the mechanism is already available in this exact install, just not yet used for this purpose.

On raw token economics, Anthropic's own position is unambiguous in kind if not in exact numbers: hooks "operate outside the context window entirely, making them the most economical choice for deterministic automation," while CLAUDE.md-style prose "carries the highest token cost" because "every line loads into every session... whether it's relevant to their task or not" [^19]. No Anthropic-published number for the token cost of a *triggered* hook's injected text was found; third-party estimates exist (200-800 tokens per always-injecting hook; ~20-30k tokens of total fixed per-session overhead before any user input) but a live WebFetch of that source failed this session (domain-safety block) and the figures are relayed from a search snippet only — mark UNVERIFIED [^20]. A related GitHub issue in Anthropic's own `claude-code` repo (user-reported, not an official benchmark) measured roughly 37KB/804 lines of always-resent context per turn from CLAUDE.md/rules/memory/skill-listing/MCP-schema overhead combined, and is filed as a duplicate — i.e. multiple users have independently raised the same overhead concern [^21].

### The "left for you" failure mode, and how other frameworks close it

Anthropic's own Claude Code best-practices doc names the underlying dynamic directly, even without using the literal phrase "left for you": "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop: every mistake waits for you to notice it" [^6]. Its prescribed fix is to "give Claude something that produces a pass or fail" so "the loop closes on its own" rather than on the human [^6] — precisely the shape of fix recommended here (a Stop hook that produces a pass/fail on the response itself). The "Building Effective Agents" post frames human involvement as bounded, deliberate checkpoints — "agents plan and operate independently, potentially returning to the human for further information or judgement," pausing "at checkpoints or when encountering blockers," not as a default end-of-task dump [^7]. A companion Anthropic post on a real multi-agent build harness shows the same principle enforced structurally: a QA pass catches gaps and hands them back to the *generator agent* to fix, not to a person [^8].

Other frameworks encode this as an explicit second pass rather than trusting one model's self-discipline: Cursor ships a dedicated verifier-subagent role, invoked "after tasks are marked done to confirm implementations are functional," instructed plainly "do not accept claims at face value, test everything" [^13]. Cognition's Devin runs its own change end-to-end with computer use and returns screen recordings as proof before a human ever reviews it, explicitly to avoid "unverified changes" becoming "unmanageable" at scale [^14]. The Reflexion paper formalizes this as a memory-carrying self-critique loop between attempts [^15]. Microsoft's Magentic-One paper documents the negative case that matches today's incident almost exactly: agents "consistently did not utilize available data, tools, or resources effectively... even when automation was an option," citing "manual downloads persisting when FileSurfer was available for rapid document retrieval" as a named example [^16] — structurally the same failure as leaving a Windsurf settings check or a window close as manual follow-up when a tool for exactly that already existed.

OpenAI's consumer-facing agents (Operator, ChatGPT agent) encode the opposite triage explicitly and by design: they are trained to *proactively hand control to the human* for logins, payments, and CAPTCHAs specifically, and confirmation prompts before consequential actions "reduced the risk of model mistakes by approximately 90%" [^9][^10]. This is a different problem than today's (those are genuine hand-off-required cases, not "the tool could have done this but nobody asked it to"), but it establishes the shape OpenAI itself validates: an explicit, named category of things to hand off, with everything else defaulting to autonomous action. Codex CLI encodes the same idea as a configuration axis rather than a prompt rule: `approval_policy = "on-request"` acts autonomously within the sandbox and only asks when leaving it; `"never"` is the documented mode for fully unattended runs [^11][^12].

### The two concrete cases today, verified directly against the plugin's own source

**Reading Windsurf's Cascade > MCP > Configure screen to confirm a path.** `computer_snapshot` reads any window's full accessibility tree with no grant required — "Reading is free. Acting needs a grant, per app, for that session only" [^35]. A settings screen, like a menu or dropdown, opens its own window/hwnd and is read the identical way as any top-level window [^36]. Windsurf, as an editor, sits in tier `shell`: "readable, never typeable" [^35][^36] — which is exactly what's needed here, since confirming a displayed path is a read, not a keystroke. The one real documented failure mode is **BLIND TREE**: an Electron app with its renderer accessibility bridge off returns an empty tree with no error, fixable by launching it with `--force-renderer-accessibility`, with a screenshot fallback available either way [^35][^36]. No Windsurf-specific carve-out exists in either doc — this is generic, untested-for-this-app-specifically tooling, so whether Windsurf's *particular* settings screen hits BLIND TREE is itself unverified without running it, but nothing in the documented design would have stopped the attempt [^35][^36][interpretation].

**Closing a stray window on a second virtual desktop.** Verified directly in `server/index.mjs`: `computer_close_window` (line 1581) calls `offDesktopCheck(win)` (line 581), which only produces a refusal `'other_desktop'` error when the install's `DESKTOP_SCOPE` setting equals `'current'` (line 582) [^37]. The shipped default is `'all'` [^35], under which this check returns `null` and the close proceeds straight through to `driver.call('close_window', { hwnd, mode })` (line 1591) [^37] — i.e., **under the default configuration, closing a window on another virtual desktop is not blocked at all.** This lines up with the README's own documented limit, which names *frame*-level actions — "title bar, minimise, maximise, **close**" — as exactly what Windows continues to serve for a window on a desktop you aren't looking at, withholding only its *contents* [^35]. Microsoft's own docs back this at the OS level: `IVirtualDesktopManager` exists specifically because ordinary window handles remain fully addressable across desktops (`GetWindowDesktopId`, `IsWindowOnCurrentVirtualDesktop` exist to let an app *check* desktop membership, which wouldn't be necessary if handles simply stopped working cross-desktop) [^22][^23], and neither `DestroyWindow` nor `WM_CLOSE`/`PostMessage` documents any virtual-desktop restriction anywhere in their reference pages [^26][^27]. A companion local test script, `tools/desktop-test.mjs`, is documented as creating a second virtual desktop and exercising exactly this path, including closing it again, as part of the plugin's own test suite [^35][sq5 finding]. The repo's own same-day TODO notes a caveat worth carrying forward rather than treating this as unconditional: "Do not close it by switching the user's screen; the user closes it" [^39] — read together with the source-verified frame-level close path, the safest reading is *close via the frame-level `computer_close_window` call directly, without ever switching the active desktop* (which the code already supports and does not require); actually switching the user's screen to reach the window would be the wrong approach and is a different action than what `computer_close_window` does [^37][^39][interpretation]. One real edge case neither doc addresses: if closing triggers an on-screen confirmation dialog (e.g., "save changes?"), that dialog would appear on the hidden desktop where neither Claude nor the user can see or answer it without switching — worth a smoke test before treating "just close it" as unconditionally safe [interpretation].

## Contradictions & Open Questions

- The repo's own TODO note ("the user closes it" [^39]) reads, on its face, as advising against automated closing at all, while the source code and README both confirm the frame-level close is unblocked by default and has a dedicated test [^37][^35]. Resolved above as "don't switch desktops to do it, but the direct frame-level close is fine" — but this is this report's interpretation, not a restatement of an explicit prior decision, and is worth a one-line confirmation from whoever wrote the TODO note before treating it as settled [interpretation].
- Whether Windsurf's specific Cascade/MCP settings screen has a healthy (non-BLIND) accessibility tree is unverified — no source names Windsurf specifically; this can only be settled by an actual `computer_snapshot` run against it [^35][^36].
- Exact token-cost figures for hook-injected context (200-800 tokens per hook; ~2,400 for four; ~20-30k fixed session overhead) come from a single third-party Substack post that could not be re-fetched this session (only a WebSearch snippet was available) — treat these numbers as directionally plausible but UNVERIFIED, not as a citable benchmark [^20].
- No primary Anthropic or Microsoft source states in one sentence "a background/other-desktop window's HWND can be acted on via PostMessage/WM_CLOSE without switching desktops" — this report's conclusion is inferred from the *absence* of any documented restriction in the relevant API reference pages, not a single quoted confirmation [^26][^27][interpretation].
