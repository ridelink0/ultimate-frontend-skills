# Third-party skill packs for ultimate-frontend-skills (UFS) to absorb

Research date: 2026-09-20. Repos cloned with `git clone --depth 1` into
`scratchpad/packs/<name>` (paths given per pack). Star counts, licence SPDX
ids and fork status pulled live from the GitHub REST API
(`api.github.com/repos/<owner>/<repo>`), not from marketing pages. Where a
claim could not be directly confirmed on disk it is marked UNVERIFIED rather
than smoothed over.

Read first, per the task: `C:\Users\OWNER\cinematic-web-design\skills\ultimate-frontend-skills\references\skill-packs.md`
and `plugins.md`. The handshake model they establish: an installed pack owns
its domain while live, UFS defers silently inside that domain, and nothing is
ever recommended to the user mid-build. Every verdict below is written against
that model.

## Part 1 — the five named packs

### 1. Taste Skill — Leonxlnx/taste-skill

- **Repo:** https://github.com/Leonxlnx/taste-skill
- **Runner-up by stars (also a "Taste Skill"):** https://github.com/codeswithroh/tastemaker (397 stars, MIT) — grounds AI UI in real reference images + a persistent per-developer taste profile. Both are genuinely about frontend design taste; Leonxlnx is the pick for depth (10 skill variants vs. one) and stars.
- **Stars:** 88,798 (Leonxlnx) vs. 397 (tastemaker) — two orders of magnitude apart.
- **Licence:** MIT (`LICENSE`, copyright Leonxlnx, 2026).
- **Install:** `npx skills add https://github.com/Leonxlnx/taste-skill` (all skills), or `--skill "design-taste-frontend"` for just the default.
- **Cloned to:** `scratchpad/packs/taste-skill`
- **Skills shipped** (10, one line each):
  - `taste-skill` (install name `design-taste-frontend`) — default anti-slop landing/portfolio/redesign skill, v2 experimental, three-dial system (VARIANCE/MOTION/DENSITY).
  - `taste-skill-v1` — the frozen original, for projects that depend on its exact behaviour.
  - `gpt-tasteskill` (`gpt-taste`) — stricter GPT/Codex-oriented variant, more aggressive GSAP direction.
  - `image-to-code-skill` — generate reference images, analyse them, then implement to match.
  - `redesign-skill` — audit an existing UI first, then fix.
  - `soft-skill` — calm, expensive, high-end visual variant.
  - `output-skill` — anti-laziness/anti-placeholder enforcement.
  - `minimalist-skill` — Notion/Linear-style restrained UI.
  - `brutalist-skill` — Swiss type, raw mechanical contrast (beta).
  - `stitch-skill` — Google Stitch-compatible rules with a `DESIGN.md` export mode.
  - Plus three image-generation-only skills: `imagegen-frontend-web`, `imagegen-frontend-mobile`, `brandkit`.
- **Does well:** unusually concrete, numeric rules instead of vibes — banned hex families for the "premium-consumer beige+brass" cluster with exact codes, a named rotation of alternative palettes, an eyebrow-label ratio ("max 1 per 3 sections, mechanically countable"), hero hard limits (headline ≤2 lines, subtext ≤20 words), a CTA-intent dedupe rule, and working GSAP sticky-stack/horizontal-pan code skeletons with the exact ScrollTrigger footgun called out (`start: "top top"`, not `"top 80%"`). The italic-descender-clipping rule (`leading-none` clips `y g j p q` in italic display type) is a genuine, specific bug callout.
- **Weaknesses observed:**
  - The main `taste-skill/SKILL.md` is **1,207 lines / ~35,000 tokens in one file**, with no reference-file split — everything loads whether the task needs it or not. UFS's own pipeline deliberately keeps `SKILL.md` short and pushes depth into `references/`, loaded on demand; this pack does the opposite.
  - Despite an FAQ claim of being "framework agnostic," §3 bakes in React/Next.js RSC, Tailwind v4, and the `motion/react` library as hard defaults — a real contradiction inside the same document.
  - The README embeds referral/affiliate links for paid API sponsors (Kimi, Fluxion AI) inline in an ostensibly technical taste document — a bias/monetisation concern in a tool whose entire pitch is disinterested taste.
  - No accessibility guidance beyond two contrast-ratio call-outs; nothing on focus order, ARIA, or screen readers.
  - The banned-palette lists are asserted with no citation or dataset, unlike UFS's `data/awards.json`, where every entry carries a `verified` flag and unusable-URL rows are dropped at merge time.
- **Improvements UFS could take:**
  1. Adopt the mechanical, countable pre-flight checks (eyebrow ratio, CTA-word-count, hero line caps) as literal `audit.mjs` counters, the way `audit.mjs` already counts `<em>`/`<i>` for the one-italic-word rule.
  2. Adopt the "don't repeat the same palette family twice in a row" anti-repetition rule as an explicit `awards --pick`-style diversity check.
  3. Borrow the VARIANCE/MOTION/DENSITY 1–10 dial vocabulary as a shorthand *description* of UFS's own presets, without copying its text.
  4. Add the italic-descender-clearance check to whatever checks display type.
  5. Do **not** adopt its React/Tailwind/Motion default stack — conflicts with UFS's plain-HTML/`core.css` chassis.
- **Overlap with UFS:** heavy, on exactly the ground `tells.md` and `typography.md` already cover (banned palettes, banned fonts, anti-slop defaults) plus the component-motion ground `emilkowalski/skills` already owns per `skill-packs.md`. Per the handshake model: if installed, it would own "anti-slop frontend defaults for a component/page," and UFS would defer to it silently, with `tells.md`/`typography.md` standing in when it is absent.

### 2. Impeccable — pbakaus/impeccable

- **Repo:** https://github.com/pbakaus/impeccable
- **Stars:** 69,386. **Licence:** Apache-2.0 (frontmatter says "Apache 2.0"; GitHub API confirms `Apache-2.0` SPDX).
- **Install:** `npx impeccable install` (npm CLI) puts the skill in place; once installed it is driven as `/impeccable <command>`.
- **Cloned to:** `scratchpad/packs/impeccable`
- **Skills shipped:** **one** skill, `impeccable` (v4.3.1), deliberately consolidated (per its own `CLAUDE.md`: "Do not add standalone skills... the `/` menu pollution problem is real") into 24 commands, one line each:
  - `craft` — deprecated alias for an ordinary build request.
  - `shape` — plan UX/UI before writing code.
  - `init` — capture durable product context into `PRODUCT.md`.
  - `document` — generate `DESIGN.md` from existing code.
  - `extract` — pull reusable tokens/components into a design system.
  - `critique` — heuristic UX review.
  - `audit` — technical checks (a11y, perf, responsive).
  - `polish` — final pre-ship quality pass.
  - `bolder` / `quieter` — amplify or tone down.
  - `distill` — strip to essence.
  - `harden` — production-ready errors/i18n/edge cases.
  - `onboard` — first-run flows, empty states.
  - `animate` / `colorize` / `typeset` / `layout` / `delight` / `overdrive` — enhancement commands.
  - `clarify` / `adapt` / `optimize` — copy, device-adaptation, performance fixes.
  - `live` / `generate` — in-browser visual-variant iteration.
  - (utility, not counted in the 24: `doctor`, `hooks`, `pin`.)
- **Does well:** the single-skill, many-commands architecture is a real, considered answer to command-menu bloat — directly relevant if UFS's own five-command surface (`webdesign`, `debug-website`, `design-handoff`, `awards`, `atelier`) ever grows. The engine is a genuine Rust rule-checker (`crates/core`, `crates/foundation`) with an oracle/golden-test regression suite, not just prose — closer to a linter than a prompt. Its "Modes" taxonomy (Persuade / Operate / Read / Experience, orthogonal to a separate web/iOS/Android/adaptive "Platform" axis) is a clean, reusable way to separate "what is this surface for" from "what does it run on." Its "verify in bounded passes, not a loop... the ceiling covers the whole cycle" instruction is close to a word-for-word match for the cost-discipline UFS's own AGENTS.md and `verify` command already care about. It explicitly credits its `ios.md`/`android.md` as distilled from MIT-licensed `ehmo/platform-design-skills` (see item H below) with attribution in `NOTICE.md` — the correct way to vendor a third party's work.
- **Weaknesses observed:**
  - This is not a portable skill folder so much as a full product: a Cargo workspace, a wasm bundle, a Chrome extension, an npm CLI shim, and a **private companion repo** (`impeccable-site`) that holds the paid catalog explicitly withheld from the open repo ("Never add catalog data files back to this repo; the catalog is the paid-service moat"). UFS's own `data/awards.json` corpus is fully open by contrast.
  - Every command shells out to a **downloaded, version-pinned binary** (`~/.impeccable/bin/<version>/…`) resolved by a `sh` launcher — real external-code-execution surface that conflicts directly with UFS's own constraint ("Zero dependencies. Node 18+, built-ins only... do not add a dependency block").
  - The `SKILL.md` frontmatter `description` field is a dense run-on list of nearly every UI-review synonym (audit, polish, harden, adapt, colorize, i18n, empty states, edge cases…) to maximise auto-trigger surface — functional, but a heavier context cost at the very first turn than a narrower description would be.
- **Improvements UFS could take:**
  1. Adopt the Persuade/Operate/Read/Experience vocabulary as a layer over UFS's own presets (bone/ink/cinema/fable) to separate surface-intent from visual direction.
  2. Reuse the "verify in bounded passes, not a loop" phrasing near-verbatim in `verify`'s own documentation.
  3. Follow its citation pattern exactly if UFS ever vendors `ehmo/platform-design-skills` for native guidance: name it, license it, put attribution in a `NOTICE.md`.
  4. Study the single-skill/many-commands router if UFS's command surface grows past what one table can hold cleanly.
  5. Do **not** adopt the downloaded-binary launcher — it is the single clearest violation of UFS's own zero-dependency rule among anything in this report.
- **Overlap with UFS:** the largest of the five. `critique`/`audit`/`polish`/`bolder`/`quieter`/`distill`/`harden`/`onboard`/`animate`/`colorize`/`typeset`/`layout`/`delight`/`overdrive`/`clarify`/`adapt`/`optimize` collectively span almost everything `audit.mjs`, `look`, `quality`, `typography.md`, `motion.md` and `craft.md` do for an *existing* UI. If installed, per the handshake model it would own essentially the whole "revise an existing surface" domain end to end, and UFS's own checks would stand in only when it is absent — the starkest total-overlap case in this report.

### 3. Playwright CLI — microsoft/playwright-cli

- **Repo:** https://github.com/microsoft/playwright-cli (a standalone repo, **not** inside the `microsoft/playwright` monorepo — confirmed by GitHub search after the direct URL 404'd on the monorepo path).
- **Stars:** 13,455. **Licence:** Apache-2.0.
- **Install:** `npm install -g @playwright/cli@latest`, then `playwright-cli install --skills` (writes `.claude/skills/playwright-cli` or, with `--skills=agents`, `.agents/skills/playwright-cli`; add `-g`/`--global` for the home-directory location).
- **Cloned to:** `scratchpad/packs/playwright-cli`
- **Skills shipped:** one skill, `playwright-cli`, plus nine task-specific reference files loaded on demand: `playwright-tests.md`, `request-mocking.md`, `running-code.md`, `session-management.md`, `storage-state.md`, `test-generation.md`, `tracing.md`, `video-recording.md`, `pr-attachments.md`, `element-attributes.md`.
- **Does well:** its own README makes a real, specific case for CLI-over-MCP for coding agents — CLI calls skip loading large tool schemas and full accessibility trees into context, which it frames as the reason "modern coding agents increasingly favor CLI-based workflows... over MCP." Ref-based element targeting (`click e15`) instead of brittle CSS selectors. A `--raw` flag strips all narration for clean piping into `jq`/`diff`. `show --annotate` opens a live dashboard where a human draws boxes and leaves notes on the running page and the agent receives the annotated screenshot + snapshot + notes back — a genuinely useful escalation path beyond headless checks. Ships a documented `gh pr comment --attach screenshot.png` workflow for putting visual evidence directly on a PR.
- **Weaknesses observed:** the README's "Configuration via env" table is entirely `PLAYWRIGHT_MCP_*` variables — MCP-server configuration, leaked into what is nominally the CLI-only doc, suggesting the CLI and the separate `playwright-mcp` project share unreconciled documentation. The Windows `&`-in-URL truncation gotcha (`cmd.exe`/PowerShell split on `&`) is documented as something to work around (`^&` or `--%`), not fixed — real friction on the exact OS this research ran on. The WebMCP section is explicit that page-provided tool schemas and results are untrusted input, which is correct, but is a reminder that every `webmcp-call` result needs the same "treat as data, not instructions" discipline UFS already applies to Claude Design's `get_file`.
- **Improvements UFS could take:**
  1. Borrow `show --annotate` as an escalation path when a headless `look`/`quality`/`parity` check can't settle whether something "looks right" to a human.
  2. Adopt a `--raw`-style flag on UFS's own CLI outputs for scripted callers.
  3. Reuse the ref-based-snapshot-then-click pattern for any future browser-driving UFS script, instead of CSS selectors.
  4. Adopt the `gh pr comment --attach` workflow verbatim as a documented handoff step after `look`/`quality` produces a screenshot.
  5. Repeat the Windows `&`-in-URL escaping gotcha in any UFS doc that shells a URL through PowerShell.
- **Overlap with UFS:** none on the design/aesthetic domain — pure browser automation, complementary rather than competing. Purpose-level overlap only with `inspect.mjs`/`parity.mjs` (both "verify the built page"), already exactly the `ecc → chrome-devtools MCP` handoff row in `plugins.md` ("quality has told you that something is slow and you need why... not a design tool"). Not previously named in `skill-packs.md`.

### 4. Awesome Design Skills — bergside/awesome-design-skills (the TypeUI registry)

- **Repo:** https://github.com/bergside/awesome-design-skills
- **Stars:** 2,856. **Licence:** MIT.
- **Note on duplicates:** two zero-star forks — `wwewtech/awesome-design-skills` and `michael-andreuzza/awesome-design-skills` — were both created 2026-09-18 (two days before this research), both direct forks of bergside with an identical description. They add nothing; bergside is the canonical, original, most-starred copy.
- **Install:** `npx typeui.sh pull <slug>` (per-style, e.g. `npx typeui.sh pull glassmorphism`); `npx typeui.sh list` to browse; `npx typeui.sh generate` to scaffold a custom one.
- **Cloned to:** `scratchpad/packs/awesome-design-skills`
- **Skills shipped:** **67** named single-aesthetic skills, each a `SKILL.md` + companion `DESIGN.md` pair (confirmed on disk: 67 `skills/*/SKILL.md` files present). A representative slice, one line each by name only (all follow the identical two-file shape): `glassmorphism`, `brutalism`, `neobrutalism`, `minimal`, `material`, `claymorphism`, `skeumorphism`, `neumorphism`, `retro`, `riso`, `dithered`, `sketch`, `doodle`, `bento`, `mono`, `terracotta`, `cosmic`, `matrix`, `pacman`, `tetris`, `sega`, `roku`, `shadcn`, `claude`, `impeccable`, `codex`, `agentic`, `stitch`, `storytelling`, `vintage`, and 37 more (full list in the README).
- **Does well:** cleanly splits the machine-facing instruction file (`SKILL.md`: tokens, component rules, a11y constraints, quality gates) from the human-facing rationale (`DESIGN.md`) — a split UFS does not currently make (its `references/` are agent-facing only, with no parallel human-rationale document). Breadth is real: 67 distinct, narrowly-scoped aesthetic directions is far beyond any single pack in this report (taste-skill ships ~10 variants).
- **Weaknesses observed:**
  - Two of the 67 slugs are literally **`claude`** and **`impeccable`** — third-party aesthetic-style presets named after other tools/companies with no affiliation to them. A user running `npx typeui.sh pull impeccable` gets a 1-of-67 style preset from this registry, **not** the real `pbakaus/impeccable` skill reviewed above. This is a genuine naming-collision risk worth flagging plainly rather than smoothing over.
  - Given the time budget for this task, I read the registry index, the README, and confirmed the 67-file layout on disk, but did **not** read an individual style's `SKILL.md`/`DESIGN.md` content in depth — per-skill instruction quality is UNVERIFIED beyond the two I opened to confirm the file shape.
  - The repo ships 244+ marketing preview PNGs (one per style, `registry-examples/*.png`) — presentation weight with no bearing on instruction quality, and a real chunk of clone size.
- **Improvements UFS could take:**
  1. Adopt the `SKILL.md`/`DESIGN.md` split as a documentation pattern for UFS's own presets (bone/ink/cinema/fable) — right now the "why" for a preset lives only in scattered prose across `references/`.
  2. Cite the breadth-over-depth contrast explicitly when explaining UFS's choices: this pack proves 67-shallow is a real, viable model, which makes UFS's 4-deep model a considered choice, not a gap.
  3. Borrow the `--dry-run` preview flag idea for any future UFS scaffolding command.
  4. **Do not** let UFS ever name a preset after another tool or company — the direct lesson from this pack's `claude`/`impeccable` slugs.
  5. If UFS ever adds a "browse directions" command, prefer real UFS-rendered previews (its own `study`/`awards` contact sheets) over static marketing PNGs that can drift from the underlying instructions.
- **Overlap with UFS:** partial, at the "pick a named aesthetic direction" layer only — UFS's own preset system and `taste-skill`'s minimalist/brutalist/soft variants solve the same problem at different grain (UFS: 4 deep; taste-skill: ~10; this registry: 67 shallow). Not previously listed in `skill-packs.md`.

### 5. 3dviz-pro-max — viettranx/3dviz-pro-max

- **Repo:** https://github.com/viettranx/3dviz-pro-max
- **Stars:** 474. **Licence:** MIT for the repo's own code/data. Explicitly **not** covered by that MIT grant: BodyParts3D anatomy meshes (CC BY-SA 2.1 Japan) and the bundled Outfit/JetBrains Mono fonts (SIL OFL 1.1) — correctly disclosed in the README rather than blanket-licensed.
- **Install:** symlink `skills/3dviz-pro-max` into `~/.claude/skills/3dviz-pro-max`, or `claude --plugin-dir /path/to/3dviz-pro-max` (checkout or packaged zip). A `/plugin marketplace add viettranx/3dviz-pro-max` route exists but is **explicitly marked untested by the authors themselves**.
- **Cloned to:** `scratchpad/packs/3dviz-pro-max` (first clone attempt hit Windows's `MAX_PATH` on a deeply nested `evidence/dataset-changes/.../knowledge.reasoning-boundary-conditions-are-the-model` path and failed with "Filename too long"; succeeded on retry with `git -c core.longpaths=true clone`).
- **Skills shipped:** one skill, `3dviz-pro-max`, a 10-step workflow (intent+direction → object reasoning → ground the representation → construction routing → quality targets+tool discovery → first view → meaningful behaviour → run+inspect → refine → honest report), backed by 223 recipes across 24 subject directions (environments, characters/motion art, products, architecture, anatomy, physiology, molecules/materials, solid geometry, linear algebra, calculus, probability, topology, logic/circuits, algorithms, twisty/spatial puzzles, rigid mechanics, soft/fluid/thermal, waves/optics, robotics, earth/environment, astronomy, abstract systems), 440 knowledge records, 22 kit blueprints, 37 style profiles, and Python helper scripts (`search.py`, `resolve.py`, `design-context.py`, `host-probe.py`, `capture.py`).
- **Does well:** an unusually rigorous, self-critical "Honest limits" section in its own README: it states plainly that knowledge records are "editorially reviewed authoring guidance — not runtime observations," names exactly which kit tiers are proved (T2 on 18/22, T3 on 2 Blender bakes) versus which "ships nowhere" (T4), and reports its own before/after eval (19→23→23→25 of 30 across four with-skill runs vs. a baseline of 21) while explicitly cautioning that n=1-per-condition "is not a demonstration that the skill makes better scenes." This is exactly the "never pretend stuff" discipline done well by a third party. Its "never describe an unobserved frame" rule and `capture.py` real-GPU-screenshot discipline mirror UFS's own `look`/`verify` philosophy closely.
- **Weaknesses observed:**
  - This is a 3D-scene/Blender/Three.js content skill, not a page-layout skill — adjacent to UFS's actual domain (typography, motion, page composition), not inside it.
  - Genuinely large: 2,112+ tracked files including hundreds of evidence/showcase images, one path deep enough to break a plain `git clone` on Windows (see Install above) — a live portability problem on exactly this session's OS.
  - The flagship demo asset, `harness-village.gif`, is explicitly disclosed as pre-dating the skill and containing a Vietnamese-language UI — "historical footage, not an English demo or a runtime test of the skill." Good disclosure, but it means the single most impressive visual in the repo cannot be attributed to the skill's own output.
  - The marketplace/plugin-install route is self-reported as untested.
- **Improvements UFS could take:**
  1. Adopt the "Honest limits" section format nearly verbatim for UFS's own README/`pipeline.md` — one place stating exactly what in `data/awards.json` is verified vs. not, and what `webdesign verify` does and does not prove.
  2. Borrow "never describe an unobserved frame" as a stated hard rule for `look`/`quality`/`parity`.
  3. UFS's own `blender.mjs` is the one real overlap point — this pack's `references/blender-threejs-handoff.md` is worth a read as a second opinion on tool-responsibility splitting, since UFS's `references/three.md` is deliberately narrower (scroll-driven product pages only).
  4. Treat the MAX_PATH failure as a live cautionary example if UFS's own `data/awards/*.json` chunking or evidence habits ever nest folders as deeply.
  5. The construction-routing table (reuse / adapt / author custom / use external asset / combine — each row naming "what to preserve") is a reusable decision-table shape UFS could apply to `imagery.md` ("stock photo vs. generated asset vs. cut-out").
- **Overlap with UFS:** minor, at the Blender/Three.js tooling layer only (`scripts/blender.mjs`, `references/three.md`); none on 2D layout, typography, or page-level motion choreography. Brand new (created 2026-09-10), not previously listed in `skill-packs.md`.
